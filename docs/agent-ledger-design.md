# Agent 账本模块（Ledger）设计提案

> 日期：2026-08-01
> 状态：设计阶段（模块边界已收敛，数据契约待评审）
> 协作能力：MCP / 连接器（数据来源）、Skill（执行方法）；其他模块由 Agent 按需调用

---

## 一、背景：连续自动化任务的价值困境

### 问题

Agent 的连续性自动化任务（每天查金价、每天生成日报、每天监控指标）目前存在一个结构性缺陷：**任务重复执行，但毫无积累。**

以"每天查询金价"为例：

- 第 1 天：查今日金价 → 输出一个数字 → 结束
- 第 30 天：还是查今日金价 → 输出一个数字 → 结束

每次都调用 API、每次都拿到数据、每次都丢弃。任务退化为**纯粹的 API 调用**——没有比较、没有趋势、没有归因，更没有随时间的增值。

### 根因

现有能力模块各有分工，但缺了"事实积累"这一层：

| 模块 | 职责 | 数据形态 | 能否积累事实 |
|------|------|---------|-------------|
| Wiki | 语义知识（结论、解释） | markdown 页面 | 保存的是"总结"，不是"事实" |
| Skill | 执行方法（怎么做） | SKILL.md | 保存的是"流程"，不是"数据" |
| MCP / 连接器 | 获取外部数据 | 临时响应 | 用完即弃 |

Agent 缺少一个**属于自己的、跨时间累积的结构化数据层**。

### 核心洞察

> **Agent 需要时间维度：拥有过去，而非总结过去。**

Wiki 是"总结过去"，账本才是"拥有过去"——把每次任务产生的结构化事实积累为 Agent 自己的数据资产，让重复任务的数据随时间形成完整历史。

---

## 二、模块定位：Agent 的「事实账本」

### 定义

> **账本是产品为 Agent 提供的一级数据能力模块——Agent 的"事实账本"。它让 Agent 拥有时间维度：把每次任务产生的结构化数据可靠地记录下来，并提供快速回顾、查询、聚合和分析所需的数据基础。账本本身不做语义解释、不做价值评判，也不决定数据是否值得沉淀或下一步应该采取什么行动；这些判断由 Agent 根据任务上下文自主完成。**

### 与现有模块的关系

```
MCP / 连接器  →  账本（事实数据）  →  Agent 回顾、分析与决策
     获取数据       记录、查询、计算          │
                                             ├─ 回答当前任务
Skill（定义怎么采集、怎么分析）───────────────┤
                                             ├─ 发起受控治理
                                             └─ 可选调用其他能力（如 Wiki）
```

- **账本存事实与数值**（发生了什么、数值是多少），并提供快速查询、聚合和质量信息
- **Agent 解释数据**（数据意味着什么、是否重要、下一步做什么）
- **Skill 存方法**（如何采集、如何分析、何时调用治理能力）
- **Wiki 是 Agent 可选择的下游能力之一，不是账本的依赖、固定出口或验收条件**

### 与外部数据库的本质区别

| 维度 | 传统数据库（面向应用开发） | 账本模块（面向 Agent 使用） |
|------|--------------------------|---------------------------|
| 使用入口 | 应用代码或人工查询 | Agent 可直接调用的受控工具 |
| schema 定义 | 人事先设计 | Agent 按需声明，内核负责校验 |
| 数据回顾 | 需要编写查询与业务逻辑 | 提供时间范围、维度与聚合查询 |
| 数据治理 | 外部系统或人维护 | Agent 发起决策，内核按确定性规则执行 |
| 安全边界 | 依赖数据库权限 | 写入、查询和治理能力在工具层受控 |

这不是让账本替 Agent 判断数据价值，而是给 Agent 一本可以快速记账、查账和分析的结构化数据账本。

### 非职责边界

账本明确不负责以下事项：

- **不做价值评判**：不判断某条数据、某个趋势或某个数据集是否“重要”“低价值”或“值得沉淀”
- **不做语义结论**：不替 Agent 生成业务结论、归因解释或长期知识总结
- **不决定下一步行动**：不自行决定是否补采、清理、归档、调整采集频率或调用其他模块
- **不绑定外部出口**：不把 Wiki、报告、通知或任何外部模块作为固定流程的一部分

账本的输出应始终是事实、统计结果、质量状态、容量状态和可执行的治理能力；这些输出供 Agent 快速回顾和分析，再由 Agent 决定下一步。

## 三、价值论证

这里的“价值”指账本为 Agent 提供的数据能力价值，不是账本对数据或结论做价值评判。账本只负责可靠记录、快速回顾和可验证计算；数据是否重要、是否需要继续采集、是否应该沉淀到其他模块，均由 Agent 根据任务上下文决定。

### 价值四层（因果链）

**第 1 层 · Agent 能力：从无状态到有历史**
没有账本，Agent 每次执行都是"失忆的表演"。有了账本，Agent 第一次拥有跨时间的自己：能回答"趋势如何"，而不只是"现在多少"。

**第 2 层 · 任务质量：重复任务产出持续升值**
同一个任务，成本不变，产出随时间增长：
- 第 1 天：`今日金价 462.5`
- 第 30 天：`今日金价 478.2，30 日均价 470.1，本月 +3.4%，处于近 30 天高位`

这就是对抗"任务退化"的机制——不是任务变了，是任务的产出被时间放大。

**第 3 层 · 用户体验：看见 Agent 在变聪明**
用户发现 Agent 记得上周的数据、会主动指出"这周波动比上周大"。留存不是靠功能多，是靠积累深。

**第 4 层 · 产品壁垒：数据资产与生态差异**
Agent 积累越久越懂用户，迁移成本随时间上升——这是竞品无法快速复制的护城河。

### 适用边界（诚实分析）

账本不是给所有任务用的，适用于：**可重复 + 可量化 + 有时间价值**的任务（监控、行情、日报、健康数据）。一次性任务不需要账本。

### 验证方式

以金价场景为第一个 demo：连续运行 30 天，对比"有账本 vs 无账本"的回顾与分析能力差异，验证 Agent 是否能更快获得完整历史数据并完成趋势、波动和异常对比。

## 四、设计原则

1. **计算优先于语义检索** — 账本服务于数值计算（聚合、趋势、异常），存储选 SQLite 单文件，而非 markdown。原因是"要查询和计算"，不是"要语义检索"。
2. **写路径唯一** — 所有数据只能通过 append 进入，自动注入时间戳与来源。破坏性操作在结构上不存在。
3. **数据有生命周期，容量有边界** — 账本不是无限增长的库；它按明确的保留、聚合和归档策略控制容量，不自行判断数据是否“有价值”。
4. **治理能力内建，治理决策外置** — 质控（lint）、聚合（rollup）、提炼（distill）、清理（prune）是模块的一等能力；账本负责按确定性规则安全执行，何时调用以及如何解释结果由 Agent 决定。
5. **保持简单** — 核心动作只有：记（append）、查（query）、算（aggregate）、检（lint）、治（治理执行）。Agent 需要的是一本便于快速回顾和分析的数据账本，不是一个替它思考的数据库管理系统。
6. **只提供数据能力，不做价值判断** — 账本不判断数据是否重要、不决定结论应沉淀到哪里，也不把任何外部模块作为固定出口。

## 五、数据模型

### 数据集（Dataset）抽象

Agent 不面对数据库文件，只面对"数据集"——类似于它自己的私有指标表：

```
数据集 = 定义（schema + 用途）
      + 数据行（指标值 + 采集时间 + 来源）
      + 采集记录（执行历史）
```

### 核心表结构（MVP）

```
datasets   (id, name UNIQUE, schema JSON, description, retention_policy JSON, created_at, updated_at)
records    (id, dataset_id FK, payload JSON, observed_at, ingested_at, source_type, source_id, dedupe_key, schema_version)
runs       (id, dataset_id FK, execution_id, operation, status, started_at, finished_at, meta JSON)
```

- `observed_at`：事实发生或数据源声明的时间，用于按业务时间进行回顾和分析
- `ingested_at`：账本服务端实际入账时间，由内核生成，用于追踪延迟和补采
- `source_type` / `source_id`：由可信执行上下文注入，例如 connector、cron job 或 execution id；外部响应中的来源信息只能作为 payload 或非可信元数据保存
- `dedupe_key`：按数据集声明的身份字段生成或校验，防止重复执行导致数据污染
- `schema_version`：记录写入时使用的 schema 版本，避免后续 schema 演进影响历史解释
- `runs`：记录账本操作的执行情况，并通过 `execution_id` 关联外部自动化执行记录，不重复定义自动化生命周期

### Schema 演进

- 字段可追加（Agent 今天建 3 个字段，明天加 1 个）
- 字段不可随意删除（避免历史数据错位）
- 数据形态变化走"新数据集"而非"改旧表"
- schema 声明应包含字段类型、指标/维度角色、单位、时区和版本号；半动态 payload 只应出现在声明过的字段内，未知字段由内核校验后决定是否保留，而不是直接放行

## 六、核心行为与工具接口

### 工具集

| 工具 | 动作 | 职责 |
|------|------|------|
| `ledger_create` | 记前准备 | 声明数据集 schema、身份字段与保留策略 |
| `ledger_append` | 记 | 追加一条记录（唯一写入口，自动注入入账元数据） |
| `ledger_query` | 查 | 只读查询历史数据（必须指定数据集与范围） |
| `ledger_aggregate` | 算 | 按时间/维度聚合（avg/sum/min/max/count） |
| `ledger_stat` | 算 | 按确定性算法计算统计特征（移动平均、波动率、趋势系数等），只返回数值，不做语义解读 |
| `ledger_lint` | 检·质控 | 数据健康检查：缺失、异常值、重复 |
| `ledger_rollup` | 治·聚合 | 按 Agent 指定或数据集策略将原始数据聚合为摘要（降采样） |
| `ledger_distill` | 治·提炼 | 按明确算法将摘要计算为统计特征，不生成语义结论 |
| `ledger_prune` | 治·清理 | 按明确的时间、容量或状态条件执行受控清理，不判断“低价值” |

### 分析能力分层（安全边界）

| 层 | 能力 | 护栏 |
|----|------|------|
| 第 1 层 | 预定义 API（append/query/aggregate/stat/lint） | 覆盖日常回顾需求，写路径唯一 |
| 第 2 层 | 只读 SQL（SELECT + 聚合 + JOIN） | 语法校验、强制 LIMIT、超时；禁写操作 |
| 第 3 层 | 只读计算脚本（沙箱） | 预注册、读数据快照副本，原始数据不可被改动 |

**底线：写操作永远只走 API；读操作可以逐层放开。** "受控"不是限制能力上限，而是把高风险操作从结构上排除。

## 七、数据治理与生命周期

### 生命周期分层（层层蒸馏）

```
原始数据（热）      逐日明细          按数据集策略保留
   │  rollup 聚合
聚合摘要（温）      周/月均值与高低点   按数据集策略保留
   │  distill 计算
统计特征（冷）      波动率、趋势系数    供 Agent 快速回顾
   │  query / aggregate / stat
计算结果            数值与统计量         返回 Agent 自主分析
```

### 治理机制

- **质控（lint）**：按照 schema 和质量规则报告缺失日期、异常值、重复记录等问题；账本不自行推断业务影响
- **聚合（rollup）**：按照数据集策略或 Agent 明确给出的时间范围与粒度，将明细计算为周/月摘要
- **提炼（distill）**：按照明确算法计算波动率、趋势系数等统计特征，为 Agent 快速回顾提供数据
- **清理（prune）**：仅按照明确的时间、容量、记录状态或 Agent 指令执行受控清理，不以内置“价值分数”决定去留

### 自主治理原则

Agent 通过账本返回的数据量、完整性、新鲜度、异常、聚合状态和容量信息，自主决定是否补采、聚合、提炼、归档或清理。账本负责提供可观察状态和安全、确定性的执行能力，**不替 Agent 判断数据价值，也不自行选择治理目标**。

## 八、落地路线

### 阶段一：MVP（本地优先）

- SQLite 单文件，存放于 `~/.thething/ledger/`
- 核心工具：`ledger_create / append / query / aggregate / lint`（`stat`、`rollup`、`distill`、`prune` 按需开放）
- 治理工具：`ledger_lint / rollup / prune`（`stat`、`distill` 可后置）
- 金价 demo：定时任务 → 采集 → 落库 → 快速回顾 → 聚合分析 → Agent 自主判断下一步
- 验证：连续运行 30 天，对比有无账本时 Agent 获取历史、完成统计和识别异常所需的步骤与结果

### 阶段二：管理界面

- 用户可查看 Agent 有哪些数据集、数据量、采集历史
- 手动清理、导出数据
- 数据集健康度可视化（哪些天没采到数据）

### 阶段三：云同步与共享

- 数据随账号走，多设备一致
- 跨 Agent 共享数据集（受控权限）
- 分层结构原样迁移到云数据库（只读账号 + 视图权限对应既有设计）

## 九、待决策问题

1. **数据集 schema**：预定义严格 schema vs 允许半动态（payload JSON + 推荐字段）？倾向后者，给 Agent 灵活性同时保留查询能力
2. **保留时长默认值**：原始数据 90 天 / 摘要 1 年是否合理，是否需要按数据集类型差异化
3. **治理触发方式**：纯策略（定时执行）vs 策略 + Agent 自主判断（推荐后者，符合"自治"定位）
4. **容量配额**：单数据集 / 总配额上限与超限行为（拒绝写入 vs 自动降采样）
5. **工具命名与注册**：与现有 `agent/tools.ts` 注册机制的对齐方式，工具描述措辞（引导 Agent 正确使用）

## 十、验收标准

1. **积累**：同一任务运行 30 天后，Agent 能一次查询获得连续历史，并完成时间范围内的对比、趋势和异常分析
2. **回顾效率**：Agent 无需重新调用外部数据源或逐条读取历史任务输出，即可按时间、维度和指标快速回顾数据
3. **自主治理**：账本能返回数据量、完整性、新鲜度、异常、聚合状态和容量信息，Agent 可据此自主决定并发起补采、聚合、归档或清理
4. **职责边界**：账本只返回事实、统计结果和治理状态，不输出“重要/无价值/应沉淀”等语义判断，也不依赖 Wiki 或其他外部模块
5. **容量有界**：连续运行 3 个月，账本可按明确策略执行 rollup/prune，不依赖账本自行评判价值
6. **安全**：Agent 无法通过任何工具绕过 append 写入事实，治理操作受权限、范围和审计约束
7. **简单**：一次采集任务只涉及 2-3 个工具调用（create → append；需要回顾时 query / aggregate）
