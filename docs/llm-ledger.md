# LLM Ledger

给 Agent 建立持久事实层的一种模式（A pattern for giving agents a persistent, compounding fact layer）。

这是一份 idea file，设计来直接复制给你的 LLM Agent（WorkBuddy、Claude Code 等均可）。它的目标是传达高层思想；具体的存储引擎、表结构、工具命名、目录布局，由你的 Agent 与你协作展开。

## 核心思想（The core idea）

大多数 Agent 自动化任务的体验看起来是这样：每天查一次金价 → 得到一个数字 → 输出 → 结束。第二天重复。第 30 天还是重复。每次调用外部 API、每次都拿到数据、每次用完即弃——任务退化为"带调度的 API 调用"。这能用，但没有任何东西被积累。问一个需要跨 30 天数据的问题（"最近波动怎么样？"），Agent 只能从外部世界重新获取、重新拼装，每次都从头开始。没有构建起任何东西。

这很像 RAG 的困境：每次提问都从原始文档重新检索、重新推导，知识从未被真正建立起来。区别在于，RAG 缺的是**知识的积累**，这类任务缺的是**事实的积累**。

这里的想法不同。与其让每次任务都回到外部世界重新获取数据，不如让 Agent **增量构建并持续维护一个持久账本**——一个结构化、随时间累积的事实层，位于 Agent 与外部世界之间。当任务产生数据时，Agent 不只把它显示出来，而是把它记录进账本；当下次任务需要"趋势、对比、波动、历史"时，它直接查账本，而不是重新获取。

关键区别：**账本是一个持久、复利的事实工件。** 历史已经在那里，时间与来源已经注入，缺失已经被标记。账本随每一次记录变得更完整，Agent 随每一次任务变得更了解自己的过去。

Agent 很少（或不再）需要回到外部世界重取历史——那正是账本存在的意义。

这适用于很多场景：行情监控、每日数据采集、健康数据、日报生成——任何"可重复 + 可量化 + 有时间价值"的任务。一次性任务不需要账本。

## 架构（Architecture）

三层：

**外部世界（Raw sources）** —— MCP 服务器、连接器、API 响应。瞬时、可变，Agent 只从中读取，从不修改。这是事实的源头，不是事实的家。

**账本（The ledger）** —— 结构化的数据集（datasets）与记录（records）。Agent 决定记录什么、以什么 schema 记录；一个确定性内核负责校验、幂等、注入时间与来源、维护索引。append 是唯一写路径，破坏性操作在结构上不存在。你（或 Agent）读取它；它保存事实。

**Agent（解读层）** —— 查询、聚合、计算、判断价值、决定下一步。**账本不做价值判断、不做语义总结**；"这意味着什么、是否重要、下一步做什么"，由 Agent 根据任务上下文自主完成。

此外还有一层**配置/编排**：数据集 schema 定义，以及告诉 Agent"何时使用账本、如何编排操作"的 Skill。这层是让 Agent 成为"有纪律的事实记录者"而非"随手记笔记的聊天机器人"的关键。它随使用共同演化。

## 操作（Operations）

**Append（记）** —— 唯一写路径。任务产生可量化、未来可能被对比的数据时，Agent 追加一条记录。内核自动注入时间戳与来源，按数据集声明的身份字段做幂等去重。"要不要记"这件事不应留给每次对话重新思考——它被业务 Skill 的采集步骤（以及在编写该 Skill 时明确的 Ledger 用法）固化为默认行为。

**Query / Aggregate / Stat（查 / 算）** —— 只读操作。按时间范围与维度查询历史；按指标聚合（均值、极值、计数）；按确定性算法计算统计特征（移动平均、波动率、趋势系数）。Agent 拿到数值后自行解读，账本不解释。

**Lint（检）** —— 健康检查。缺失日期、异常值、重复记录、数据新鲜度。账本报告问题，不推断业务影响。

**治理（可选，后置）** —— 按明确的时间或容量策略执行聚合降采样（rollup）与受控清理（prune）。规则确定、执行受控、留有审计；账本不自行判断"哪条数据没有价值"。

## 索引与日志（Indexing and logging）

两个特殊视图帮助 Agent（和你）导航账本，职责不同：

**catalog（目录）** 是内容导向的。列出所有数据集：字段、时间范围、记录数、最近更新、健康度。Agent 面对任务时先看目录——感知自己"拥有"什么，再决定是去外部世界取新数据，还是从账本回顾历史。规模中等时（几十个数据集）目录足够，无需向量检索。

**runs（日志）** 是时间导向的。记录每次采集、分析、治理操作：何时、针对哪个数据集、结果如何。它是账本演化时间线，帮助 Agent 理解最近发生过什么（例如"昨天采集失败了"）。追加写入，可用简单工具按时间筛选。

## 可选工具（Optional tools）

规模上来后，可能需要小工具帮助 Agent 更高效地操作账本：

- **只读 SQL 层**：允许任意 SELECT + 聚合查询，带语法校验、强制 LIMIT、超时；禁写操作。读能力可以逐层放开，写路径永远只有 append。
- **计算脚本沙箱**：预注册的分析脚本，读取数据快照副本，原始数据不可被改动。
- **管理界面**：查看数据集、数据量、采集历史、健康度可视化；手动清理与导出。

## 与 Wiki 的关系（How it relates to the wiki）

如果你的 Agent 还有语义知识层（参见 llm-wiki 模式），两者互补：**账本存事实与数值，wiki 存结论与解释。** 事实先进账本；"数据意味着什么"由 Agent 判断；是否沉淀为 wiki 页面、沉淀什么，也由 Agent 决定。账本不依赖 wiki，wiki 也不强制消费账本——它们是平行资产，由 Agent 在正确时机各自使用。

## 为什么有效（Why this works）

Agent 的弱点是记不住、算不准、会漂移。让 LLM 口算 30 天均值、凭印象判断波动，结果不可靠；让它自己维护"今天的数据和上周比怎么样"这类状态，它会忘记。

账本把这两件事交给确定性引擎：记录不会丢，统计不会算错，缺失可以被检测。Agent 省下"重新获取 + 重新记忆"的开销，把精力放在它擅长的事情上——判断、解释、决策。

人也一样。手工记账的负担会随规模增长，人最终会放弃；账本让维护成本趋近于零，记录持续发生，时间维度随之积累。

在精神上，这与 Memex 的"关联足迹"一脉相承——不过这里积累的不是文档间的关联，而是事实的时间序列：**Agent 拥有自己的过去，而非总结过去。**

## Note

这份文档有意保持抽象。它描述模式，不描述实现。具体的存储引擎（SQLite 单文件？）、表结构（datasets / records / runs？）、工具命名（ledger_append？）、目录布局——取决于你的领域、你的偏好、你的 Agent。以上一切皆可选、可模块化：数据全是数值就不需要复杂 schema；规模小就不需要只读 SQL 层；你也许只想要"记录 + 回顾"，不要治理。正确的用法是把它交给你的 Agent，共同实例化一个适合你的版本。它的唯一工作是传达模式。你的 Agent 能搞定其余部分。
