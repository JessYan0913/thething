## 1. 问题定义与现状

### 1.1 战略判断（为什么值得做）

**todos 是 agent 自主完成长任务的关键，是进入「更智能、更能干事」新水平的门槛。**
LLM 本质无状态，长任务自主依赖把执行状态外化到上下文之外：压缩存活、中断恢复、
子 Agent 交接、进度可验证、失败自纠。todos 就是这面承重墙——它的可靠性决定能力上限。

### 1.2 症状

「agent 有时候建 todo，有时候不建，不稳定」——同类请求行为不一致。

### 1.3 根因分析（最终理解）

关键区分：**判断 vs 行动**。基线证明模型判断并不差（单步从不误建、多数多步任务能建），
掉链子的是**判断之后不照做**——系统从不提醒，模型干着干着就"忘记"规划。所以解法不是
让代码替模型判断，而是**提醒 + 让模型自己判断**。

| # | 根因 | 说明 |
|---|------|------|
| 1 | **零提醒（主因）** | 系统从不主动提示/提醒模型考虑规划（触发仅靠系统提示词一段散文），判断→行动的桥断了 |
| 2 | 判断依据错 | 即使被提醒，标准是"多步/多项交付物/多次操作"——按实现结构而非**心智复杂度**，抓不住真正该拆解的任务 |
| 3 | 双入口打架 | submit_plan 与 todo_write 都自称「首选」，模型多一层判断（§5 已澄清） |
| 4 | 行动无代价 | 该建没建没有任何负反馈（lint 只在已建时触发） |
| 5 | 兜底是死的 | 5 步无活动提醒在 todo 为空时不注入（pipeline 快照依赖 snapshot 非空，已修死） |

### 1.4 量化基线（Phase 0，deepseek-v4-pro）

用 `scripts/todo-baseline/` 在真实模型上无头跑 14 条固定请求（编码/非编码多步、单步、
边界、短句复杂任务、认知复杂决策）+ 多次重复：

| 指标 | 值 |
|------|----|
| 多步建单率 | **≈ 40%**（15 次多步运行建单 6 次） |
| 单步/模糊误建率 | **0%** |
| 建单后推进/result 完备率 | 100%（一旦建单质量优秀） |
| 同请求多次运行 | g01 1/7、g03 3/4、c02 1/3（行为分裂） |

**结论**：薄弱环节全在冷启动触发（rung-1），不在使用质量。模型一旦建单即规范（单一
in_progress、逐步更新、result 完备）。

> 注：基线过程曾发现 todo 写库 `FOREIGN KEY constraint failed`——是 harness 未先建
> conversation 行的工件，非产品 bug（真实流程发消息时自动建会话行）。Phase 0 报告在
> 14:53 之前生成的均为该假数据，已删除。

### 1.5 概念演进（三轮校正，终态依据）

| 轮 | 做法 | 为什么弃用 |
|----|------|-----------|
| 1 | 正则/关键词判「是否多步」（`looksMultiStep`/`executionIntent`）+ 执行型硬注入反复提醒 | "顺便/还有"等话术判不出；判断质量不如模型。**分类该交给模型** |
| 2 | 字数门限判「是否超短」（`isTrivialRequest`，<12 字跳过） | "请给我生成一个贪吃的游戏"很短却是复杂任务。**字数与复杂度无关** |
| 3 | 按「步骤/交付物/操作」教模型判断（终态前的框架） | 一个 10 步的机械活不需要 todo，一个 2 步的重大决策非常需要。**复杂度 = 心智复杂度，不是实现步骤数** |

**终态原则**：判断全部交给模型，判断依据 = 心智复杂度（问题需不需要拆开思考），
代码只做确定性机械活——何时提醒。

## 2. 方向框架：从「看板」到「账本」

todos 当前是**看板**（模型自觉维护的展示），要成为**账本**（执行状态的可靠事实源）。

**账本承重原则**：让账本成为执行状态的唯一可靠来源，让保持账本准确成为 agent 的最优策略。
子 Agent 交接只走账本、压缩后只能从账本恢复、离开账本就吃亏（委托丢结果/压缩失忆）→
维护账本变成理性选择而非提示词吩咐。这时「善于利用 todos」是内化的，不是被教导的。

**七级阶梯**（利用质量，逐级递进）：

| 级 | 行为 | 状态（2026-08-15） |
|----|------|----|
| 1 | 建——复杂任务开头拆清单 | ✅ Phase A 规划触发（LLM 判断 + harness 提醒） |
| 2 | 推——每步推进更新状态 | ✅ 已具备 |
| 3 | 验——完成写 result | ✅ 已具备 + lint |
| 4 | 循——失败写 error + 修订计划 | ✅ 快照含 error + 快照富化 |
| 5 | 托——委托传 todoId 回写账本 | ✅ 已实现（Phase B 钉死不变量） |
| 6 | 存——压缩/中断后账本仍准确 | ✅ 架构天然成立 + 快照富化 |
| 7 | 纳——把账本当唯一事实源规划下一步 | 部分（提示层已教，未强制） |

## 3. Phase A：规划触发（rung 1-2）

### 3.1 设计（终态：LLM 判断 + harness 提醒，判断依据 = 心智复杂度）

`packages/core/src/modules/agent-control/plan-prompt.ts`：

- `buildPlanPrompt()`：开工前轻问一句——"todo 的作用是拆分复杂任务。如果你判断这个请求
  有较高复杂度（需要把较大问题拆成几个子问题来思考和完成：涉及多方面 / 有取舍 / 结果
  不确定 / 要探索迭代），**即使实际步骤不多**，也请先用 todo_write 拆成任务清单；如果
  简单直接（答案明确、一步完成），直接回答"。**判断交给模型**。
- `buildEmptyTodoReminder()`：5 步兜底——"如果这个任务较复杂、值得拆解推进，先建清单；
  确认简单直接就忽略"。**不预判复杂度，由模型再判断一次**。

`pipeline.ts` 两处注入（均无任何预判门槛）：

1. **开工前提示**（step 0，清单为空）：注入 `buildPlanPrompt()`——每条请求都问，由模型判断。
2. **5 步兜底**（清单为空 + 5 步无活动）：注入 `buildEmptyTodoReminder()`。**修死了原
   空清单不注入的死路径**。

不再有执行型/内容型的硬软分叉、不再按"开始干活"反复念叨、不再有关键词/字数门限、
也不再按"步骤/交付物"教模型——判断完全交回模型，harness 职责收敛为"提醒"。

### 3.2 验证（同一 harness，deepseek-v4-pro）

| 用例 | Phase 0 基线 | 终态 |
|------|------|------|
| g01 行程 | 1/7 | **稳定 2/2**（step0 建 4-5 项） |
| c02 重构 | 1/3 | ~1/2（模型判断有波动，建单那次推进到完成） |
| g02 整理 | 0/1 | ~1/2（内容型，模型常判"可直接总结"） |
| g05 决策 | — | 0/2（信息不足先 ask_user_question 澄清，未触发拆解） |
| c03 贪吃蛇（短句复杂） | — | 0/1（模型判"单文件直接写"，step0 write_file） |
| 单步误建率 | 0% | 0% |

> 解读：g05/c03 这类**给了模型判断机会但模型选择不建**的案例，正是"判断交模型"的
> 应有表现——单案例不夸大新框架的增量，c02/g02 的 ~50% 波动是模型判断的固有方差。

### 3.3 天花板（诚实记录）

无论谁做判断（规则或模型），**提醒终究是"话"，模型可以无视**（c02 曾多次提醒仍直接干完）。
逼近 100% 需**工具级强制**（清单不存在时拦截非 todo 工具执行），风险：可能死锁（模型
不建单就卡住）、改变用户可见行为。见 §6。

## 4. Phase B：账本承重（rung 5-7）

### 4.1 摸底结论：B1-B4 大多已实现

| 项 | 状态 | 证据 |
|----|------|------|
| B1 子 Agent 交接闭环 | ✅ 已实现 | agent-tool/parallel-agent-tool 传 todoId；executor 启动置 in_progress、成功 completeTodo(result.summary)、失败 failTodo(error)；updateTodo metadata 合并（父整表替换不抹子结果）；工具描述已教父传 todoId |
| B2 压缩存活 | ✅ 架构天然 | 账本 SQLite 持久化（压缩只动消息历史）；压缩后快照自动再注入；todo-overview 常驻系统提示 |
| B3 中断恢复 | ✅ app 层已处理 | 未完成任务检测 + 停止时 todo 状态管理 |
| B4 verify→result | ✅ 已实现 | verify 字段 + lint 警告 + result 写入 |

### 4.2 真正缺口：闭环无自动化验证

`ledger-load-bearing.test.ts`（8 条不变量，`modules/todos/__tests__/`）钉死：
- 委托回写：completeTodo/failTodo 把 result/error 写进账本、启动置 in_progress
- 父 todo_write 整表替换不抹子 Agent result（metadata merge）
- 已完成 todo 豁免整表替换（父漏传不删）；活跃项按语义删除
- 快照作为压缩/续做依据：含 result/verify/error

### 4.3 压缩快照富化（B2 续做依据）

`buildCompactTaskSnapshot` 新增：待办/进行中附 `(verify: …)`（怎样算做完）、失败区
`[!] #id subject: error`（修订计划依据）、统计含失败数。压缩后注入的状态成为完整续做来源。

## 5. A4/A5：双入口路由澄清

原 submit_plan 与 todo_write 描述都自称「首选」（"Prefer this over..."），模型随机挑、
有时两个都不用。已澄清：

- **submit_plan 描述**：收窄为仅「用户明确要求先确认」或「高风险（不可逆/对外发送/删数据）」
- **task-planning 段**：明确「其余复杂任务一律用 todo_write，不要调用 submit_plan」
- **todo_write 描述**：主规划入口，按心智复杂度判断是否拆解（见 §3.1）

验证：g01 不再误用 submit_plan（直接 todo_write）；全量 1050 tests 通过。

## 6. 剩余方向（待决策）

1. **工具级强制**（把建单率推向 ~100%）：清单不存在时拦截非 todo 工具执行，返回
   「先建清单」错误。需设逃生（如 N 次后放行）防死锁。改变用户可见行为，需谨慎。
2. **遥测/指标**：建单率、推进率、result 完备率的持续观测（harness 已具备，可接入）。
3. **恢复续做显式化**：resume 时显式注入「上次进行中任务 + 已完成结果」的续做提示。
4. **落文档/README**：向产品文档同步「agent 会自动规划」的用户侧预期。

## 7. 附录：如何复跑基线

```bash
# 全量 14 条（约 15-30 分钟，需 ~/.agents/models.json 与 API 可用）
pnpm --filter @the-thing/core exec tsx ../../scripts/todo-baseline/run.ts

# 指定用例 + 重复采样（量化不稳定）
pnpm --filter @the-thing/core exec tsx ../../scripts/todo-baseline/run.ts --cases=g01,c02 --repeat=3

# 常用参数：--model=deepseek-v4-flash（低成本） --timeout-ms=120000 --max-steps=12
```

安全：resourceRoot/dataDir/configDir 全指向临时沙箱，不触碰真实 ~/.thething；禁用
mcps/connectors/skills。报告输出到 `outputs/todo-baseline/`（latest.json 最近一次）。
